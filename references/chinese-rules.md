# 受控中文技术写作规则

本文给出适合中文技术文档的详细规则。规则继承 ASD-STE100 Issue 9 的目标，但不逐句翻译英文规则。

## 1. 术语和词义

### 1.1 一个概念对应一个首选术语

- 同一文档内，同一对象不得交替使用近义名称。
- 如果“任务、作业、活动”“检查、验证、确认”表示不同概念，必须分别定义。
- 首次出现的缩略语应给出全称。行业内约定无需展开的缩略语可以保留。
- 接口字段、代码标识符、状态常量和界面标签按源文本保留，不因语言统一而改写。

### 1.2 技术术语必须可定位

优先使用国家标准、行业标准、项目术语表或用户提供资料中的名称。没有权威名称时，选择短、具体、易区分的名称，并在全文一致使用。

不要把“有关模块、相关人员、对应数据、指定位置”当作独立术语。写明模块、人员、数据或位置的具体名称。资料未给出时，写明待定项。

### 1.3 不用修辞代替指标

“先进、强大、可靠、高效、智能、显著”等词不能证明性能。删除这些词，或改写为资料中已有的指标、适用范围和验证证据。

## 2. 名词组和定语

中文没有英文名词串的同一形式，但容易形成长定语和多层“的”结构。

- 一个名词前出现三个以上意义层级时，优先拆句或改成“对象 + 关系”的结构。
- 让数量、范围、否定和状态修饰语紧邻其对象。
- 长技术名称首次写全称。后续使用已经定义且唯一的简称。

示例：

- 不清楚：`用于目标航迹实时更新的多源传感器数据融合处理模块接口状态监控功能`
- 清楚：`系统监控数据融合模块的接口状态。该模块融合多源传感器数据，并实时更新目标航迹。`

## 3. 动作、主体和情态

### 3.1 使用直接动词

删除没有独立含义的动作壳：

- `进行日志的分析` → `分析日志`
- `开展参数配置工作` → `配置参数`
- `实现对状态的监控` → `监控状态`
- `予以记录` → `记录`

“进行、开展、实施、实现、完成”本身有技术含义时可以保留。例如，“完成握手”描述协议状态，不应机械改成“握手”。

### 3.2 写明动作主体

- 多主体文档必须写明“操作员、系统、控制器、测试人员”中的哪一个主体执行动作。
- 被动结构只有在执行者未知、无关或有意隐藏且不影响责任理解时才能使用。
- 如果一句话出现两个主体，分别写明每个动作属于哪个主体。

### 3.3 统一情态词

同一文档应定义并统一使用约束词。没有项目约定时，按下列方式理解：

| 词 | 用途 |
|---|---|
| 必须 | 强制要求，不满足即不合格或不能继续 |
| 应 | 规范性要求；如允许偏离，必须说明批准条件 |
| 可以 | 明确许可或能力，不表示强制 |
| 不得 | 明确禁止 |
| 可能 | 不确定事实或风险，不表示必然发生 |
| 预计 | 有依据的预测，必须能追溯依据 |
| 建议 | 非强制方案 |

不得在改写中提高或降低约束强度。不要把“应”统一替换为“必须”，除非适用规范已经这样定义。

## 4. 句子、指代和逻辑

### 4.1 一句一个中心

一句只写一个主要动作、要求或判断。以下情况拆句：

- 一个句子包含多个先后动作；
- 一个句子同时给要求、原因、例外和结果；
- “并、且、以及、同时、然后、随后、从而”连接了不同责任主体或不同验收点。

同时动作或不可分组合动作可以保留。例如，“按住释放按钮并拔出插头”只有在两个动作必须同时发生时才合写。

### 4.2 不省略必要成分

中文允许省略主语，但技术文本只在执行者显而易见时省略。跨步骤、跨段落或多主体场景必须重复主体。

不要写：`检查接口，异常时重启后再次确认。`

改写为：

1. `运维人员检查接口状态。`
2. `如果接口状态为“异常”，运维人员重启接口服务。`
3. `服务重启后，运维人员再次检查接口状态。`

### 4.3 限制代词

“其、该、此、这、上述、相关、前者、后者”只有在唯一先行词紧邻时才可使用。否则重复对象名称。

不要写：`控制器向终端发送密钥，随后更新其状态。`

“其”可能指控制器、终端或密钥。应根据事实写成“控制器状态”或“终端状态”。如果资料未说明，不得猜测。

### 4.4 明确条件和范围

- 前置条件放在动作前：`当指示灯变绿时，按下启动按钮。`
- 充分条件使用“如果……，则……”。
- 必要条件使用“仅当……时，才……”。
- 例外使用“除……外”或“除非……”。
- 否定词紧邻被否定内容。
- “均、分别、至少、至多、仅、全部、任一”紧邻作用对象。

不要用“在必要时、视情况、原则上、一般情况下”隐藏决策条件。写明谁依据什么条件作出决定。

### 4.5 使用显式连接关系

连接词必须说明真实关系：

- 时间：首先、随后、完成 X 后；
- 条件：如果、仅当、除非；
- 因果：因为、因此；
- 对比：但是、而；
- 例外：除……外。

不要用“同时”表达“另外”。不要用“以及”掩盖步骤顺序。

## 5. 程序、需求和 Agent 指令

### 5.1 程序步骤

每个步骤按需要包含以下字段：

1. 前置条件或触发事件；
2. 执行主体；
3. 一个主要动作和对象；
4. 可观察结果或成功标准；
5. 失败条件和处理动作；
6. 输出及其位置。

原始资料未给出某字段时，只在该字段影响执行或验收时标记缺失。不得自行补齐技术方案。

### 5.2 命令形式

面向操作员的步骤用直接命令，例如“关闭电源”。多主体流程写成“测试人员关闭电源”“系统保存日志”，避免读者猜测执行者。

### 5.3 注释

“注”只说明背景、解释或辅助信息。下列内容不得放在注释中：

- 必做动作；
- 安全动作；
- 验收阈值；
- 失败处理；
- 限制或禁止事项。

### 5.4 需求可判定性

每条需求应尽量具有唯一编号、责任主体、触发条件、系统行为、约束和验收方式。不要在一个“应”后并列多个可独立验收的行为。

## 6. 描述、方案和报告

- 从总体到局部逐步给信息。
- 每段只说明一个主题，通常不超过六句。
- 先说明对象和结论，再说明组成、输入、处理、输出、限制和证据。
- 不把建议写成事实，不把设计目标写成已经实现的能力。
- 区分文档检查、软件测试、仿真试验、平台试验和实装验证。

建议使用显式标签：`事实`、`推断`、`假设`、`待验证`、`建议`。如果文档已有等价标签，沿用已有格式。

## 7. 安全说明

安全说明包含四个要素：

1. 风险级别；
2. 预防动作或触发条件；
3. 危险源；
4. 可能后果。

示例：

`警告：拆卸电源模块前，断开设备电源。带电端子可能造成触电或死亡。`

风险级别必须依据适用的安全标准或项目规则确定。本 skill 不替用户进行风险分级。

## 8. 标点、列表、数字和句长

- 句号表示一个完整动作或判断结束。不要用分号维持本应拆开的长句。
- 冒号用于引出列表、定义或结果，不代替条件关系。
- 括号只放补充信息、缩略语、图表编号或等价表达。强制要求不得只写在括号中。
- 三项及以上的步骤、条件或并列内容使用纵向列表。
- 列表项采用相同语法结构，并写清“和”或“或”的关系。
- 数字、单位、范围和公差遵守项目或行业标准。改写时不改变原值和单位，也不自行换算。

中文不能沿用英文按空格计词的方法。机械检查可使用有效字符数作为复核信号：严格文本超过 45 个有效字符、通用文本超过 60 个有效字符时复核。字符数不是合规判据。专有名称、公式和不可分技术表达可以超过阈值。

## 9. 一致风格和最终检查

最终逐项确认：

- 同一概念是否只使用一个术语；
- 每个动作是否有唯一主体和对象；
- 每个代词是否只有一个可能先行词；
- 条件、例外、否定和范围是否附着清楚；
- 每个步骤是否只有一个主要动作；
- 约束强度和不确定性是否与资料一致；
- 数字、单位、公式、标识符和引用是否未被改动；
- 成功、失败、输出和待定项是否明确；
- 安全要求是否位于读者执行动作之前；
- 文本是否把形式检查误写成效果验证。
